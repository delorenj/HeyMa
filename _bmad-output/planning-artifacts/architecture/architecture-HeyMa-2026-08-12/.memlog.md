- (direction) Unify Wax and Vinyl beneath the repository's ./stt capability boundary; reserve ./tts for future Voxxy integration; converge user-facing controls into one tray.
- (constraint) Wax is live and stateful. Reorganization must preserve recording, source-first verified S3 archival, never-delete behavior, queue recovery, and stable deployed entry points throughout migration.
- (constraint) ./inbox is Syncthing receive-only; local recording writers continue targeting ./ingest. Repository movement must not change ingest semantics.
- (event) Architecture coaching run initialized with an architecture spine and executable migration-plan companion.
- (constraint) Current canonical Wax source is HeyMa/components/wax; ~/code/wax is a divergent two-commit legacy clone with no remote and must not be treated as canonical.
- (constraint) Vinyl is a clean, independently deployed repository with 24 tracked files, its own venv, daemon/server units, Unix RPC, state mirror, and tray process.
- (constraint) Voxxy is a substantially larger independently deployed container stack with 1266 tracked files, multiple Python dependency islands, a public HTTP/MCP contract, and significant uncommitted work; it cannot be moved safely during the first repository migration.
- (constraint) Wax and Vinyl intentionally require separate runtime Python environments. A unified tray must observe stable state/control contracts and must not import engine implementations.
- (question) Should HeyMa become the canonical source monorepo for component implementations, or remain a composition repository over independently versioned product repositories?
- (constraint) There are no current cross-product imports: HeyMa/Wax contains no Vinyl or Voxxy references, Vinyl references Wax only in a future filesystem-bridge roadmap, and Voxxy has no Wax/Vinyl/HeyMa references in its runtime surfaces.
- (constraint) Repository boundaries currently match independent deployment boundaries: waxd is a system-Python user service, Vinyl has local daemon/server/client modes in its own venv and can install on another machine, and Voxxy is a multi-container HTTP/MCP service consumed outside HeyMa.
- (constraint) The repeated concern is control-plane UI, not engine implementation: Wax and Vinyl duplicate AppIndicator lifecycle lessons, expose Unix control sockets and JSON state mirrors, while Voxxy exposes health/control through HTTP and a JSON CLI.
- (direction) Architect's current lean is a federated platform: keep independently deployable product repositories, make HeyMa the integration/control-plane repository, and build a separate unified tray over versioned adapters; do not use Git submodules as the integration mechanism.
- (question) Product identity test: should Vinyl and Voxxy remain independently installable/releasable products that HeyMa discovers, or should every install and release be owned and versioned as part of HeyMa?
- (decision) AD-1 [ADOPTED] — Federated product architecture. Binds HeyMa, Vinyl, and Voxxy ownership. Prevents independent products from becoming source-coupled merely to share a desktop UX. Rule: Vinyl and Voxxy remain independently versioned, installable, releasable, and operable products; HeyMa discovers and controls them only through versioned public adapters/contracts and never imports or vendors their implementation packages.
- (decision) AD-2 [ADOPTED] — HeyMa owns the integration control plane. Binds unified tray, stack status, cross-product workflows, deployment profiles, and integration tests. Prevents multiple products from competing to own the aggregate user experience. Rule: HeyMa owns the unified tray and normalized aggregate status/action model; each product remains the sole owner of its engine state and lifecycle.
- (direction) Wax remains canonically embedded in HeyMa during the first control-plane migration. Extraction into a standalone product repository is deferred until the adapter contract and unified tray are proven in production; extraction must preserve Git history and stable CLI/systemd entry points.
- (event) User adopted the federated product and HeyMa control-plane direction.
- (decision) AD-3 [ADOPTED] — Adapter-mediated integration boundary. Binds all HeyMa-to-product communication. Prevents runtime dependency coupling and private-state scraping. Rule: each HeyMa adapter discovers a product, reads status only from that product's public JSON/state/health surface, and invokes behavior only through its stable CLI or public API; no implementation imports, shared Python SDK, Git submodules, or direct product database reads.
- (decision) AD-4 [ADOPTED] — Bounded tray authority. Binds user-facing controls. Prevents an always-running convenience UI from becoming a destructive fleet administrator. Rule: the tray may expose safe daily controls and diagnostics—record/dictate toggles, queue inspection, health, engine selection, service restart, logs, and open-output actions—but must not expose reset, delete, purge, credential mutation, or other destructive operations.
- (decision) AD-5 [ADOPTED] — Standalone aggregate tray process. Binds desktop deployment. Prevents a UI failure from taking down any audio engine and avoids an unnecessary aggregate daemon. Rule: HeyMa runs one independently restartable system-Python heyma-tray process; products continue running in their existing services, and the tray is never required for recording, dictation, transcription, or synthesis.
- (direction) User delegated remaining non-product-level architecture choices to the architect's judgment, preferring simple, boring boundaries and minimal approval ceremony.
- (decision) AD-6 — Hexagonal control-plane paradigm. Binds HeyMa control code. Prevents GTK, CLI, and product transports from choosing incompatible domain models. Rule: the control core owns normalized snapshots, action policy, and aggregation ports; GTK tray and CLI are inbound adapters; Wax, Vinyl, and Voxxy integrations are outbound adapters that depend inward on core contracts.
- (decision) AD-7 — Dual versioned contracts. Binds separate-repository compatibility. Prevents a product JSON change from silently breaking the aggregate tray. Rule: each product owns a named, additive status schema such as wax.status.v1, vinyl.status.v1, or voxxy.health.v1; HeyMa adapters normalize those into heyma.control.v1, ignore unknown fields, and reject unsupported breaking versions explicitly.
- (decision) AD-8 — Built-in discovery with explicit overrides. Binds adapter loading and local configuration. Prevents arbitrary plugin execution and hard-coded checkout paths. Rule: first-party adapters are shipped with HeyMa; discovery probes stable executables on PATH and documented health endpoints, with command-array/endpoint overrides in XDG_CONFIG_HOME/heyma/control.toml. Missing optional products are absent, not unhealthy. No dynamic plugin loader in v1.
- (decision) AD-9 — Headless product operation. Binds every controlled product. Prevents the unified tray from becoming a runtime prerequisite or producing duplicate indicators. Rule: every product must expose UI-free status/actions and run without its native tray; Wax gains a no-tray mode, Vinyl keeps its tray separate, and Voxxy remains headless. Native trays are disabled only after aggregate-tray parity is verified.
- (decision) AD-10 — Fault-isolated observation. Binds polling, aggregation, and icon safety. Prevents one missing, slow, or malformed product from freezing or lying through the whole tray. Rule: adapters poll concurrently off the GTK thread under hard deadlines, preserve last-known snapshots as explicitly stale, and surface adapter-scoped errors. Last-known microphone-active state remains RED until a positive inactive observation; otherwise actionable attention is YELLOW and healthy/optional-absent is GREEN.
- (decision) AD-11 — Projection-only aggregate state. Binds state ownership. Prevents HeyMa and a product from both believing they own engine lifecycle state. Rule: HeyMa's aggregate snapshot is a disposable projection; product state remains authoritative. The first release has no aggregate database or daemon and may keep only in-memory last-known observations.
- (decision) AD-12 — Safe action execution. Binds adapter actions. Prevents shell injection, duplicate commands, and restarts during active capture. Rule: adapter actions are an explicit allowlist executed as argv without a shell, asynchronously, one in-flight action per component, with timeouts and preconditions; restart is disabled while that component reports an active microphone.
- (decision) AD-13 — Product-owned credentials. Binds secrets and remote access. Prevents HeyMa from becoming another credential store. Rule: HeyMa configuration stores discovery and non-secret endpoint data only; product CLIs/clients own authentication and secret retrieval, and adapters redact command output before presenting errors.
- (decision) AD-14 — Consumer-driven compatibility tests. Binds independent releases. Prevents cross-repository drift from reaching the live tray. Rule: HeyMa keeps product status fixtures and adapter contract tests for supported schema versions; each product tests its documented status surface; stack smoke tests exercise missing, malformed, stale, active-microphone, degraded-engine, timeout, and safe-action cases.
- (version) Verified desktop control-plane seed on 2026-08-12: CPython 3.13.7, PyGObject 3.50.0, GTK 3.24.50, AyatanaAppIndicator3 0.1 (package 0.5.94-1), systemd 257.9.
- (constraint) Live status reality-check: Wax, Vinyl, and Voxxy currently emit three distinct JSON shapes; Wax was actively recording during architecture work, proving repository/design changes must not restart or mutate live services.
- (constraint) Brownfield ingest conflict discovered on 2026-08-12: Syncthing still maps folder audio to ~/HeyMa/inbox as receiveonly, while deployed Wax paths and capture code treat that directory as Wax-owned local queue. AGENTS.md safety rule remains binding until a separate, byte-conserving Wax data-path migration establishes the intended dropoff/inbox ownership; the control-plane migration must not silently change either path.
- (decision) AD-7 amended — Normative dual contracts. Binds provider and aggregate JSON interoperability. Prevents same-name schemas with incompatible envelopes or enums. Rule: every provider response has root key schema with the exact product schema name, validates against product-owned JSON Schema 2020-12, and uses frozen v1 enums and semantics; HeyMa emits one exact heyma.control.v1 envelope and treats unsupported or invalid provider documents as adapter-scoped attention.
- (decision) AD-8 amended — Deterministic trusted discovery. Binds instance selection and adapter security. Prevents two HeyMa clients controlling different or counterfeit targets. Rule: an explicit XDG stanza is authoritative and suppresses fallback; otherwise a product-specific built-in candidate order is used. Executables resolve to pinned absolute regular files owned by the user or root and not group/world writable; local endpoints are default, and remote HTTP control requires explicit opt-in and verified HTTPS.
- (decision) AD-10 amended — Deterministic observation and aggregation. Binds polling, freshness, progress, and indicator color. Prevents stale, late, or malformed product output from producing contradictory tray states. Rule: the core owns one timing policy, poll sequence, non-overlapping adapter operations, stale classification, and a total RED-over-YELLOW-over-GREEN table; provider progress is displayed only with an explicit numerator, denominator, unit, and scope.
- (decision) AD-11 amended — Projection state with durable safety latch. Binds aggregate persistence. Prevents a tray restart from forgetting a last-known active microphone. Rule: product lifecycle state remains authoritative and no aggregate database exists, but HeyMa atomically persists only microphone safety latches; a latch clears only after a fresh authoritative inactive observation for the same installation or an explicit CLI retirement acknowledgement.
- (decision) AD-12 amended — Product-atomic desired-state actions. Binds safe action execution across tray, CLI, and native clients. Prevents toggle retries, stale authorization, and restart races. Rule: UI toggles resolve to explicit start or stop, every invocation carries a request id and expected provider revision, the adapter re-observes fresh state, and the product rechecks inhibitors under its own serialization and idempotency boundary. Unsafe, stale, unknown, malformed, or unreachable state fails closed.
- (constraint) Vinyl must publish one authoritative vinyl.status.v1 over its local, client, and serve roles, with product microphone-active equal to their logical OR and service-targeted lifecycle actions; the current shared mirror and local-only CLI cannot authorize aggregate controls.
- (decision) AD-14 amended — Enforceable cross-repository compatibility. Binds independent releases. Prevents provider and consumer CI from passing against divergent copies. Rule: providers publish immutable tagged schema/fixture bundles and validate real output plus backward compatibility; HeyMa pins bundle digests, tests each supported release, and owns a compatibility matrix and provider-first, consumer-next, retirement-last rollout.
- (decision) AD-15 — Operational envelope. Binds installation and process behavior. Prevents PATH Python drift and a malformed adapter from taking down the tray. Rule: HeyMa installs heyma-tray from this repository as a graphical-session user service executing /usr/bin/python3 explicitly, restarting on failure, logging to journald, and failing soft per adapter with no product Requires or PartOf relationship.
- (decision) AD-16 — Logical capability domains, physical product ownership. Binds repository reorganization. Prevents ./stt and ./tts from becoming copies, submodules, or accidental monorepo roots. Rule: stt.capture, stt.dictation, and tts.synthesis are contract metadata and navigation concepts; HeyMa stores only its control plane and embedded Wax source, while Vinyl and Voxxy stay in their own repositories.
- (event) Reviewer gate findings accepted: strengthened product-atomic safety, total freshness/indicator rules, normative distributed contracts, discovery trust, Vinyl aggregation, runtime binding, and explicit brownfield ingest nonconformance before finalization.
- (decision) AD-17 — Wax ingress ownership target. Binds the reconciliation of conflicting AGENTS, Syncthing, and deployed Wax path models. Prevents local writes into a receive-only Syncthing folder. Rule: target Syncthing receiveonly at ~/HeyMa/dropoff, which Wax only reads/copies; Wax owns local ~/HeyMa/stream and ~/HeyMa/inbox. Current AGENTS prohibition remains binding until an idle, byte-conserving migration proves the target and then updates project context.
- (decision) AD-18 — Wax receive-only importer. Binds cross-device ingress after Syncthing moves to dropoff. Prevents recordings stalling outside Wax or being copied twice. Rule: Wax continuously reconciles dropoff at boot and during runtime, ignores Syncthing temporaries, copies a stable source through an fsynced staging file, verifies content identity before atomic no-replace publication to inbox, records the import idempotently by SHA-256, and never mutates or deletes dropoff.
- (decision) AD-19 — Durable product maintenance leases. Binds safe migration and lifecycle mutation while daemons may be stopped. Prevents a CLI, hotkey, tray, or remote client starting protected work during cutover. Rule: each product persists a TTL lease with token, owner, reason, instance/epoch/revision, and expiry under the same product-wide lock used by protected actions; every start path checks it even without the daemon; acquire/renew/release are idempotent, visible in status, and expiry fails open only after the bounded TTL.
- (decision) Control contracts are normative architecture companions. Binds independently implemented core, CLI, tray, and adapters. Prevents prose sketches from producing incompatible queue, engine, action, operation, and failure models. Rule: the versioned JSON Schemas and CONTROL-CONTRACT.md in the architecture workspace are the seed authority and are promoted without semantic change into HeyMa contracts during Phase 1; product-owned schemas compose the common provider header during Phase 0.
- (decision) Provider revision semantics fixed. Binds action preconditions and workload retention. Prevents heartbeat refresh from invalidating action revisions or terminal work from persisting indefinitely. Rule: generation increments only for semantic status/action/lease changes, not heartbeat writes; updated_at refreshes every heartbeat; terminal work remains at least one heartbeat and five seconds, and removal is a semantic change.
- (decision) Observation failure projection fixed. Binds cold-start and last-known behavior. Prevents adapters classifying identical bad responses differently. Rule: unknown schema name/major is unsupported; a supported discriminator with invalid content or a missing discriminator is malformed; a prior valid row is retained stale with attention, while cold start synthesizes the exact present/reachable/unknown or present/unreachable/unknown tuple defined by the control contract.
